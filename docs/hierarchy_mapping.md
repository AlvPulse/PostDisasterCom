# Hierarchical MARL Mapping

This document maps the existing multi-agent post-disaster UAV simulator entities and concepts to a Hierarchical Multi-Agent Reinforcement Learning (MARL) framework, separating the system into High-Level Coordinators and Low-Level Workers.

## Conceptual Framework

The hierarchical control structure separates broad, strategic decisions from localized, tactical operations. This maps naturally onto the existing two-tier UAV structure without requiring changes to the core simulator semantics.

### 1. High-Level Coordinators
* **Entity Mapping:** `Relay UAVs`
* **Role:** Strategic oversight, backhaul management, and global resource allocation.
* **Responsibilities:**
  * **Routing & Topology:** Determining which Service UAVs connect to which Relay UAV to balance backhaul load and ensure connectivity to the HQ. (Maps to `RoutingAlgorithm`).
  * **Strategic Positioning (Optional in current scope):** Moving Relay UAVs to optimize coverage of the Service UAV swarm underneath them.

### 2. Low-Level Workers
* **Entity Mapping:** `Service UAVs`
* **Role:** Tactical execution, user service, and local data collection.
* **Responsibilities:**
  * **User Scheduling & Resource Block Allocation:** Selecting which active users transmit in each micro-timestep based on queue state and instantaneous channel conditions (SINR). (Maps to `SchedulingAlgorithm`).
  * **Tactical Mobility:** Adjusting position to follow clusters of users or improve A2G link quality. (Maps to `MobilityAlgorithm`).

## Concept Mapping Table

| Existing Simulator Concept | Hierarchical Framework Concept | Description |
| :--- | :--- | :--- |
| **Relay UAVs** | **High-Level Coordinators** | Agents optimizing the backhaul network, observing global or regional states to dictate routing topologies. |
| **Service UAVs** | **Low-Level Workers** | Agents optimizing A2G links, making fast, localized decisions to serve users and move accordingly. |
| **Users / Data Packets** | **Task Requests / Workload** | Packets generated by users represent the physical workload that the low-level workers must clear. |
| **Queues** | **Worker Buffers** | Queues on Service UAVs and Users represent pending tasks. High queues indicate workers that are overwhelmed or struggling with poor channels. |
| **Communication Relays** | **Backhaul Network** | The A2A links between Service UAVs and Relay UAVs. The coordinators manage this network. |
| **Spatial Positions** | **Agent State / Topology** | 3D coordinates define the constraints for both workers (A2G path loss) and coordinators (A2A path loss). |

## Integration without changing semantics

Currently, algorithms are implemented as monolithic plug-ins (`algorithms/plugin.py`) that control everything. In the future MARL setup:
1. The `AlgorithmPlugin` can remain the entry point.
2. Inside `plugin.decide()` (or `apply()`), the High-Level Coordinator policy (controlling Relay UAV routing) executes first.
3. Then, the Low-Level Worker policies (controlling Service UAV mobility and scheduling) execute, potentially conditioned on the routing assignments or macro-goals set by the Coordinators.
4. The dual-clock simulator (1s control, 1ms physics) naturally supports this: RL policies execute at the 1s control step, while the scheduling micro-decisions (`get_active_user`) can be implemented as low-level actions or derived heuristics based on RL worker parameters.
